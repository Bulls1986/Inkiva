# v0.5 Architecture TODO

This document records bounded architecture follow-ups that must be closed within the v0.5 release line. These items are not reasons to reopen ARCH-01 through ARCH-08 wholesale; they are targeted boundary corrections discovered while implementing v0.5 product work.

## ARCH-TODO-0.5-01 — Recovery Center history-service boundary

**Status:** Implementation complete; canonical CI validation pending
**Severity:** Low / architecture coupling  
**Introduced by merge/rebase:** No  
**Discovered during:** US02 crash-recovery closeout audit

### Current state

`RecoveryCenterSession` directly constructs `DocumentIntelligenceService` in order to create the Local History snapshot required before replacing a disk document with a recovery revision.

The behavior is correct, but the dependency direction is tighter than desired after ARCH-06 / ARCH-07 governance: Recovery Center currently knows the concrete history-service implementation and its storage-root construction details.

### Required v0.5 closure

Replace the direct construction with an explicit history persistence boundary owned outside Recovery Center. The final shape may be a dedicated port/service or an injected narrow interface, but it must satisfy all of the following:

- Recovery Center depends only on the operations it needs, not on `DocumentIntelligenceService` as a concrete implementation.
- Local History remains the single owner of history snapshot semantics and storage layout.
- Recovery replacement still performs: disk reread → external-change guard → pre-replace history snapshot → atomic write.
- No second history store, duplicate snapshot format, or parallel persistence owner is introduced.
- Lifecycle/ownership remains explicit and compatible with the ARCH-07 service-governance contract.
- Existing US02 recovery correctness tests remain green, with targeted coverage for the injected history boundary.

### Non-goals

- Do not redesign Recovery Center UI.
- Do not reopen the broader document-intelligence architecture.
- Do not move recovery writes into a generic background scheduler.
- Do not weaken optimistic-concurrency or atomic-write guarantees.

### Completion evidence

The item can be marked complete only when the direct `new DocumentIntelligenceService(...)` dependency is removed from `RecoveryCenterSession`, the narrow ownership boundary is documented, and focused recovery/history regression tests pass.

### 2026-09-24 closure implementation

- Added `RecoveryHistoryPersistence` / `RecoveryHistoryPersistenceFactory` under the Document Intelligence main-process boundary.
- `RecoveryCenterSession` now receives only the narrow factory and calls `createSnapshot(...)`; it no longer imports `DocumentIntelligenceService` or knows the `local-history` storage root.
- The default factory remains outside Recovery Center and is the only place in this flow that constructs `DocumentIntelligenceService` with the existing Local History root. No second store, snapshot format, or persistence owner was introduced.
- The replacement sequence is now: reread disk → compare expected revision → persist the current disk revision to Local History → read the new snapshot back after retention/quota pruning → atomic replacement → resolve the recovery revision.
- The persistence boundary throws `RecoveryHistorySnapshotUnavailableError` when the just-created rollback snapshot is no longer retained, so Recovery Center never overwrites the disk file without a durable rollback point.
- Added behavior coverage proving the injected boundary receives the current disk content before replacement and that boundary failure preserves the original disk revision and pending recovery item.
- Added `scripts/recovery-history-boundary.test.mjs` and wired it into the root `typecheck` gate so clean PR CI must protect the dependency direction.

Test-first evidence:

- Red: `node --test scripts/recovery-history-boundary.test.mjs` discovered and executed the intended test, then failed because the explicit history persistence boundary did not exist.
- Green after implementation: the same command passed `1/1`.
- Follow-up Red during the US01-US10 pre-matrix audit: the same contract was tightened to require post-prune readback and failed because the boundary only called `createSnapshot`. After adding retained-snapshot verification, it returned to `1/1` Green.
- Local Vitest and `vue-tsc` could not reach product validation in this fresh Windows worktree because the reused dependency topology stalls before Vitest discovery and fails loading `estree-walker` before Vue type checking. These are recorded as environment evidence, not product failures. The new behavior-level Vitest case and full typecheck remain required on clean CI before this item is marked fully closed.
