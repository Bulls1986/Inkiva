# Inkiva v0.6.0 — Link, Path, and Navigation Interaction Contract (V06-01)

**Status:** proposed normative contract for v0.6.0; becomes authoritative when merged into develop.  
**Date:** 2026-10-08  
**Base:** develop at planning time, v0.5.0 release line  
**Scope:** V06-02 workspace index; V06-03 link completion; V06-04 navigation; V06-05 backlinks; V06-06/07 diagnostics and repair; V06-08 rename/move consistency.  
**Higher-priority contract:** [Desktop Editor Interaction Contract](DESKTOP_EDITOR_INTERACTION_CONTRACT.md), particularly sections 2–6, 10–12, 15–16, 18–21.  
**Audit:** [V06-00 Capability Audit](https://github.com/Bulls1986/Inkiva/blob/docs/v0.6-delivery-plan/docs/product/V0.6-CAPABILITY-AUDIT.md), pending separate PR #226.

This is a **product and engineering acceptance specification**. It is not an assertion that the existing implementation already satisfies it. No product code or executable tests are changed in V06-01.

## 1. Goals and non-goals

**Outcome:** users can create ordinary portable Markdown document links, follow them deliberately, inspect backlinks and broken targets, and recover from filesystem changes without losing edits. Links should feel like part of the editor, not a separate wiki/graph application.

**In scope:** standard inline relative document links, explicit same-file fragment navigation, workspace-scoped backlink indexing, link candidate selection from the already-authoritative hyperlink action, file-existence diagnostics and explicit repair, filesystem-change safety.

**Not in scope for v0.6:** proprietary double-bracket/wiki links, transclusion, graph UI, remote crawlers, cloud sync, a new language server, bulk unused-resource deletion, converting reference-style Markdown link syntax, and a complete heading-anchor validator. Image assets remain covered by the existing image subsystem, not the new broken-document-link report.

**Compatibility:** other Markdown syntax, reference-style links, auto-links, external URLs, raw HTML anchors and additional editable file extensions keep their existing editor behavior. They are not silently treated as broken merely because the v0.6 document index does not support them.

## 2. Vocabulary, identity, ownership

- **Active document**: currently edited tab, including its unsaved current Markdown and live caret/selection.
- **Workspace**: explicit local folder selected in the file tree; a loose open file is not automatically a whole-disk workspace.
- **Indexed document**: eligible .md or .markdown file under that workspace, or a currently opened eligible document deliberately included under an explicit scope policy. Source text is always the disk file plus current dirty tab precedence; index entries are disposable projections.
- **Document link**: a standard inline Markdown link with a relative path to .md or .markdown, optionally with #fragment. External URL, fragment-only links, image links and reference-style links have distinct semantics and must not be merged into this scope by naïve string matching.
- **File identity**: path identity after safe resolution and filesystem identity checks, separate from the exact authored source spelling. Matching and normalization must respect the actual filesystem's case sensitivity. Mac volumes cannot be assumed universally case-insensitive.
- **Index revision**: identity of the workspace, document pathname and source revision from which a result was computed. Older asynchronous results must never replace newer user or file state.
- **Logical link occurrence**: source file identity plus exact link source offset/range and its source revision. A line number alone is only a display hint.

**Ownership:** Muya/document runtime owns document text and its mutation/undo history; main process owns filesystem reads/writes; preload and shared typed IPC mediate cross-process data; derived index/background tasks have no authority to overwrite a document. Do not invent a separate link persistence database or use renderer DOM as the complete index.

## 3. Supported syntax and path contract

### 3.1 Standard persisted representation

- A new local link is ordinary Markdown, for example:

  ~~~markdown
  [Guide](./docs/guide.md)
  ~~~

  Not proprietary double-bracket/wiki syntax.
- The completion UI generates a relative destination from the **source document directory** to the chosen target, preserving portable forward slashes. The result must round-trip in Source/WYSIWYG and save/reopen.
- Encode reserved characters in path segments where needed, with UTF-8 percent encoding; never encode structural path separators. A literal # in the filename must be encoded as %23; an actual #fragment remains a fragment separator. A literal percent sign must be encoded without double-encoding an already canonical destination.
- Spaces, CJK, brackets, parentheses, backslashes, quotes, percent signs and URL-reserved characters require focused parser/serializer acceptance. Preserve authored valid destinations when no edit to them was requested. Existing links with angle-bracket destinations and optional titles must not be normalized just by viewing/opening.
- A fragment-only link such as the Markdown source shown below navigates **within the active document**:

  ~~~markdown
  [Section](#overview)
  ~~~

  A normal relative document link targets another file (or the same file when explicitly named). A fragment is never treated as a filesystem segment.
- New generated destinations in the v0.6 *document-link completion/index* scope target .md or .markdown. This intentionally narrower scope does not restrict opening or editing files with other Markdown-compatible extensions elsewhere in Inkiva. Document the scope in UI states, not by falsely reporting other formats as invalid.
- No absolute machine-local path, drive-specific URI or network share path may be *silently synthesized* as a portable relative Markdown destination.
- If the active document has no saved filename, **relative-link insertion requires Save As first**. Refusal/cancel leaves the document, selection, undo stack and source unchanged. No fallback to the process working directory.
- If source and target are on incompatible filesystem volumes so a safe relative path cannot be constructed, explain the limitation and allow cancellation/manual source editing. Do not emit a fake relative path or a machine-specific path while claiming portability.

### 3.2 Resolution, case, links outside the workspace

- Resolve the encoded pathname only after identifying the path/fragment split; validate malformed escapes without throwing into the editor. Do not double-decode or interpret a user path as executable code.
- A relative link already authored to a location **outside the active workspace** is allowed to remain valid Markdown; deliberate opening follows existing filesystem protections. The workspace index must not silently recurse outside its selected root or edit those files on behalf of workspace maintenance.
- Handle Windows separators, case-only rename, Unicode and filesystem case differences according to actual resolution; never use blanket lowercasing on all macOS filesystems as a substitute for file identity.
- Symlinks: prevent cycles and unbounded traversal. Index only eligible entries according to explicit workspace boundary policy; a symlink escaping the workspace cannot grant permission to rewrite external targets. Filesystem permission errors are distinct from missing paths.
- Unsafe executable links must retain the existing security confirmation/guard rules. Link completion must never bypass file-opening safety checks.
- A target pathname used in a choice list must be backed by an actual known candidate; stale/missing candidates cannot silently result in a different same-named document.

## 4. User interaction: hyperlink editing and candidate completion (V06-03)

**One primary entry:** Ctrl+K (Windows/Linux) / Cmd+K (macOS) is Insert/Edit Link in the existing editor. Do not repurpose it for search or create a second document-link toolbar. Preserve existing hyperlink dialog/tool behavior and enhance it with a **local document candidate suggestion list** inside the existing URL/destination editing flow.

1. Selection preserved on invocation: selected text becomes the link label unless the user explicitly edits that label; an existing link opens with its current text and URL. An empty selection uses the existing link editing semantics rather than auto-inserting a guessed label.
2. Suggestions originate in the current explicit workspace's eligible Markdown file inventory and are disambiguated by relative path, not basename alone. The candidate label is human-readable; the inserted value is the canonical relative Markdown destination.
3. Filter while typing, with deterministic ordering and observable empty, loading and restricted/unreadable states; results cannot include arbitrary out-of-workspace paths as a side effect of broad background indexing.
4. Up/Down moves suggestion focus; Enter selects the focused item; Escape first closes the suggestion list, then a subsequent Escape follows the parent link dialog's cancellation semantics. Pointer choice must have the same effect as keyboard choice.
5. If keyboard input is in active IME composition, no candidate selection, link insertion, source transformation or focus transfer may happen until composition completes. Never turn an IME confirmation Enter into a link action.
6. Choosing a candidate and confirming the link is **one logical document mutation and one Undo unit**. Undo restores prior text and a meaningful selection/caret; Cancel/Escape produces zero document/history mutation.
7. On stale candidate/workspace switch/closed dialog, drop the old response; do not reopen the popup, insert into another tab or steal focus. Opening a completion is not itself a content edit.
8. Hover, narrow window, dark theme, keyboard focus and screen-reader labels inherit the desktop contract. Do not introduce an overlapping permanent title-bar search element.

**Outside this action:** the existing left-sidebar global search remains separate; candidate suggestions are not a new general filesystem search feature.

## 5. User interaction: deliberate link navigation (V06-04)

- **Single ordinary click** inside an editable link positions the caret/selection and never follows the URL automatically.
- Follow link by OS-native Ctrl+click (Windows/Linux) or Cmd+click (macOS), or by the existing explicit link-tools Jump action; keyboard-accessible controls must provide equivalent intentional action.
- Same-file fragment: resolve the document's **portable/GitHub-facing heading slug** to the corresponding editor runtime target; custom in-document anchors may use the existing safe fallback. Do not serialize private runtime slugs to saved Markdown.
- Cross-file relative path: resolve against the referring document, open/reuse exactly that target tab, then resolve its fragment **after** the target is ready (including virtualized headings). Do not accidentally use the previous tab's TOC.
- If a link target does not exist, is unreadable or its fragment cannot be located, provide explicit, non-destructive feedback and leave users able to return to their original editing position. A missing fragment does not justify rewriting the link.
- A user gesture after a queued navigation (typing, scrolling, selecting another tab or opening another document) takes precedence over stale navigation/scroll/focus completion. Never undo newer user intent.
- Opening a linked document must not overwrite a dirty active/background buffer, duplicate an already open tab or change disk bytes as a side effect. A fresh cross-file target gets editing focus when navigation genuinely completes; otherwise focus remains at the user's newer destination.
- External URLs retain the pre-existing guarded external-link flow and do not pass through local document scanning.

## 6. Workspace index, backlinks and identity (V06-02 / V06-05)

- With workspace A open, a link in saved B.md **not opened as a tab** must be discoverable as a backlink to A.md after the index becomes ready. Tabs-only indexing is insufficient.
- An open dirty tab is the authoritative current source for that same file's derived links; do not show duplicate/stale disk results while the tab is dirty. Saving, closing, renaming, moving and external disk changes reconcile to one identity under bounded freshness rules.
- Backlinks show source document identity, helpful preview/label and location. Clicking a backlink navigates to **that exact link occurrence** (source start/range), not just line start; preserve fallback if a fresh source revision invalidates the old offset.
- A current workspace switch cancels its old async work and removes the old result authority. Closing a tab alone must not erase a saved workspace file from the index merely because it is no longer a tab.
- Loading, ready-with-zero-results, partial/unreadable and failed scan states must be distinguishable. Never present a partial index as globally complete; do not equate a scan error with “no backlinks”.
- Index work must be bounded, cancellable, tied to workspace lifecycle and lower priority than editor input. No long synchronous scan, unbounded watcher accumulation, scan recursion loops or unused background writer.
- Index data remains disposable/rebuildable from source. No second Markdown persistence owner, no stale background rewrite, no hidden source mutation from viewing backlinks.

## 7. Broken local document links (V06-06 / V06-07)

**v0.6 release-mandatory diagnostic:** existence of a relative .md/.markdown *file target* in eligible indexed documents.

| Classification | Examples | User-visible treatment |
| --- | --- | --- |
| valid | Target file exists and is readable | No broken-link finding |
| missing-file | Eligible relative Markdown target does not exist | Broken link: show source location and target |
| inaccessible / unverified | Permission denied, offline mount, index failure | Separate “cannot verify” status, **not** “missing” |
| outside index scope | Existing link resolves outside workspace | Not treated as broken by the workspace-only report; still follows deliberate-open safeguards |
| unsupported syntax | Reference-style link, image, URL, raw HTML, code/fence/front matter | Not reported as a broken document link by this feature |
| fragment-only / unresolved fragment | #anchor and file.md#anchor | Preserve normal navigation; **heading-anchor validation is not an independent v0.6 release gate** |
| transient/stale | Document edited/renamed while scan in flight | Drop stale report; recalculate before actionable repair |

- Use existing Markdown-aware parsing and the same resolver/path policy as navigation and backlinks. Do not create another regex-only parser with different code-span/escaping behavior.
- Show results in an existing relevant navigation/document-intelligence surface, not a new persistent top bar. Each item exposes source filename/path, target, reason and navigation to the occurrence; keyboard accessibility is required.
- A “Locate” action is read-only. “Repair” is deliberate: inspect/select a replacement Markdown target via the canonical link dialog/candidate flow, preview the edit when content changes, and commit exactly one Undoable edit of the **active source document**.
- Cancellation, invalid target, stale revision or failed lookup must not mutate bytes or history; ask users to save/resolve conflicts where necessary rather than silently rewriting disk files.
- Diagnostics must be refreshed after the committed user edit; previous results cannot reappear from late background events.
- No auto-deletion, cross-workspace batch rewrites or implicit “fix all” in this version.

## 8. File rename/move and reference continuity (V06-08)

- Separate the filesystem move from optional **reference repair**. If the file already moved, cancelling repair **does not imply undoing the move**. Communicate precisely which operation succeeded and which references remain unchanged.
- Before changing other Markdown files, show the exact affected file count and edits, plus explicit **Update / Keep unchanged / Cancel** choices appropriate to the current operation. No silent rewrite of unopened or unrelated files.
- Existing dirty tabs cannot be overwritten by saved-disk link repair. Never choose disk bytes over a newer editor draft.
- Recheck each affected source revision immediately before mutation. On a stale source, preserve newer bytes, report the conflict and provide a safe manual review route.
- **Multiple files are not an atomic filesystem transaction.** A process may fail after an earlier file was written. Before implementing bulk repairs, define a durable before-change recovery point and an observable per-file result/reconciliation strategy; when rollback fails, retain original content/recovery evidence and report exactly which paths changed or remain inconsistent. Never report a partial operation as overall success or leave an unrecoverable silent partial state.
- Preserve unchanged Markdown bytes including title, unrelated links, external URLs and custom spacing. Do not repair unsupported/reference-style links by transforming them to another syntax without explicit scope expansion.
- Only the filesystem service owns disk writes, with the existing Local History/durability architecture as the single snapshot owner. No parallel backup store, hidden mass rewrite or new unreviewed IPC escape route.
- The existing sidebar/tree rename workflow and normal Undo semantics must stay meaningful. For multi-file disk operations, explicitly distinguish per-document Undo from filesystem recovery; do not claim one editor Undo rolls back unrelated files.

## 9. UI feedback and accessibility

- Loading/indexing: non-blocking, only show a progress indicator when perceptible; editor remains responsive.
- Zero results: clear “no links” / “no broken links found in checked scope”, **not** global correctness claims.
- Errors: show which action failed, whether disk/source remained safe, and the next available action (retry, open source, choose target, save, manual review).
- All primary link/diagnostics/repair actions are keyboard reachable with visible focus and accessible names in light/dark modes; Escape hierarchy is predictable.
- A disappearing anchor, changed current tab, changed document version or hidden virtualized DOM must never cause an unrelated file to open or a stale writer to seize focus.
- Follow existing sidebar layout, current v0.5 visual baseline and localization conventions; no extra permanent panels or duplicate command labels.

## 11. Implementation architecture and decision record

### Guarded boundaries

1. Reuse packages/desktop/src/main/documentIntelligence/markdownLinks.ts and markdownLinkIndex.ts; make indexing workspace-aware rather than standing up a second scanner/parser or new persistent store.
2. Main process handles workspace file reads, symlink/permission checks and disk mutation. Renderer owns only current editor UI/state. New IPC contracts require typed shared definitions and controlled preload APIs. Existing legacy raw event pathways may be audited separately; do not grow that bypass for new flows.
3. On rename/move, preserve Recovery Center/Local History ownership and prevent repair activity from intercepting editor hot paths.
4. Muya runtime is the source of document semantics and Undo. Background derived metadata must not become an editor/source revision owner.
5. Keep v0.5 table, images, Outline and desktop interaction correctness intact; acceptance evidence for this contract does not waive their existing gates.

### Decisions fixed for v0.6

- **D01:** Standard inline relative .md/.markdown links are the new indexed/completion/diagnostic scope; reference-style Markdown links continue as editable/navigable existing syntax but are not indexed by this release's scoped feature.
- **D02:** File existence is the mandatory broken-document-link result. Fragment validity is a navigation feedback concern, not an indexed global broken-anchor report in v0.6.
- **D03:** Link completion is embedded in the existing hyperlink command (Ctrl/Cmd+K) and UI, not the global sidebar search or an added top bar.
- **D04:** Workspace roots bound indexing and mass repair authority; deliberately opening an authored out-of-workspace link is a separate, guarded operation.
- **D05:** Multiple-file repair requires explicit recovery/partial-failure reporting; per-file atomic replacement alone does not prove multi-file consistency.
- **D06:** An already completed file move is not automatically rolled back when optional link repair is cancelled.
- **D07:** Native macOS acceptance and reference-machine performance may only be claimed after they have actually been executed; neither was satisfied by this document-only task.

### Explicit later-task choices (not covertly pre-decided by this contract)

- Exact user-facing fallback UI when source document is unsaved (reuse Save As command/prompt; do not invent a new modal without UX evidence).
- Workspace symlink traversal policy compatible with existing file tree behavior; audit real path owner and permissions before implementation.
- Specific recovery implementation for multi-file repair (rollback vs durable journal using the **existing** Local History owner); choose only after executable failure tests, architecture contract review and data-integrity analysis.
- Whether to extend supported indexed extensions beyond .md/.markdown in a later release; no implicit extension of this version's diagnostics.
