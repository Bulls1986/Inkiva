## Stage 2 — Implementation

Status: implementation completed and validated.

- Kept existing generic `mt::fs::copy` and `mt::fs::write-file` semantics unchanged. Added typed `mt::fs::copy-new` and `mt::fs::write-file-new` to shared IPC, main handler, preload and renderer-facing types. `fs.copy({ overwrite: false, errorOnExist: true })` and `fs.writeFile({ flag: 'wx' })` enforce exclusive destinations even across processes.
- Image helper now creates a unique destination using `crypto.randomUUID()` in addition to the existing timestamp/path hash. It only publishes the Markdown destination after the filesystem operation succeeds. Copying an image already at the destination remains a safe no-op.
- Unsaved documents can import absolute disk images into configured storage; a relative source path without an explicit document anchor is refused with a Save instruction, never resolved against the process CWD.
- Paste errors restore the original Markdown selection, but only when the unique loading placeholder still exists. A failed drag removes only its own still-unmodified new placeholder paragraph. Other editor edits are not undone on asynchronous failure. Standard Markdown syntax, Muya serialization and normal file APIs remain untouched.

## Scope notes / deferred

- `path` mode intentionally preserves an explicitly supplied local absolute reference. Relative placement is configurable; defaults/legacy preferences are not silently rewritten.
- V06-11 owns image resizing, missing-asset recovery and relink UX; this task does not introduce an asset manager or alter file move/rename behavior.

## Learning review

The existing generic copy/write methods remain useful for normal file operations but are not safe image-ingestion primitives when name collisions must be non-destructive. Use a narrowly typed exclusive-create/copy path rather than changing existing shared file-operation semantics.
