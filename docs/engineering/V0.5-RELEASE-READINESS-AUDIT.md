# Inkiva v0.5.0 — Release Readiness Audit

Date: 2026-10-08
Decision: **NO-GO — do not create/push a v0.5.0 tag**
Audit base: develop@4e4ae4a7cbcb2c48be144f5fbecf7e435646cae6
Scope: release evidence and traceability review only; no production-code modification, release publication, or validation-gate relaxation.

## 1. Decision summary

The recently merged desktop-interaction and table PRs show strong unit, Electron, browser, build, package-smoke, updater-artifact, and **PR fast performance** evidence. This does not establish a v0.5.0 release qualification.

**Blocking findings:**

1. **RR-01 / P0 — US11 integration is not closed.** The dedicated branch feat/us11-structured-block-keyboard contains commit 7512c4c with 12 changed files, including production Muya edits and new regressions. It is **not an ancestor** of current develop and no merged US11 PR was found. Its branch-only record covers AC-48, AC-49, AC-50, AC-77; focused tests are recorded, but a full canonical CI/merge decision is missing. Treat this as an actual unintegrated scope candidate, not as an already-shipped story.
2. **RR-02 / P0 — official reference performance qualification is absent.** The fast PR smoke gate passed for PR #217, but it is not the Windows reference P0/P1/P2 release gate. No successful official Performance Gate workflow was found among the inspected runs, and the current Actions runner API reports **0 self-hosted runners**. A September 19 reference P0 run failed at the environment check ("reference environment must run on Windows 11") before collection. Earlier BASELINE-01 measured several 50K failures, but they are historical samples, **not proof of failure on this develop head**. A valid current-tree, qualified-hardware collector → raw data → metadata → evaluator chain is required. P3 is opt-in and should not be silently promoted to a required gate.
3. **RR-03 / P0 — cross-platform release acceptance is incomplete.** Windows Electron behavior and PR macOS build/package smoke are evidenced. Native macOS titlebar/window-chrome interaction and native macOS CJK candidate-window/IME behavior are explicitly *not* accepted in the existing closeout reports. Define the supported OS matrix and execute/manual-sign the remaining native cases before release.
4. **RR-04 / P0 — v0.5.0 release candidate does not exist.** Root and desktop package versions are still 0.4.1; latest published GitHub release is v0.4.1. No v0.5.0 RC/tag/artifact set, install/upgrade/rollback acceptance, or signed-off release notes exists. The v-prefixed tag triggers release.yml, which can publish automatically once package-smoke and artifact checks pass; **do not tag until the independent release gates are approved**.

**Additional qualifiers:**

- **RR-05 / P1:** master v0.5.0 AC-to-automated-test traceability is not fully represented in one versioned repository matrix. The story records are dispersed, and some AC IDs are defined only in branch-local documents (notably US11). Do not equate "17 story names present" with every AC proved.
- **RR-06 / P1:** the PR package-smoke scripts check Windows installation and executable presence, and macOS DMG mounting/copy/executable bit and ZIP integrity. They do **not** independently prove that an installed app opens normally, preserves user documents across an upgrade, or performs a live update from v0.4.1 to v0.5.0. Add release-candidate runtime/upgrade acceptance without weakening smoke tests.
- **RR-07 / P1 (visual follow-up):** the recorded visual baseline predates September 28–29 interaction/table changes. Re-capture and audit current Light/Dark/Paper, narrow window, table/context-menu, Recent/Search, history/recovery and Source/WYSIWYG states. A visual mismatch affecting use or accessibility blocks release; cosmetic baseline refresh without a product defect may be separately scheduled.
- **RR-08 / P2 (repository hygiene):** existing task worktrees contain uncommitted changes. Do not delete them without content comparison and owner review. A prior auto-GC maintenance error should be diagnosed separately; a connectivity-only fsck returned exit 0 with dangling objects but does not replace a comprehensive object-integrity audit.

## 5. Closure plan: dependency order and exact exit criteria

1. **RR-01 — US11 scope reconciliation (P0).** From a new current-develop isolated branch, compare branch 7512c4c to latest Muya, especially US13 Undo, US08 IME, US14 Source and newer table P1. Reproduce focused Red where a gap survives; port only the required implementation and regression tests; run focused/full Muya, desktop type/lint, Chromium and relevant Electron; CI green; squash-merge and verify develop. If an intended US11 behavior is intentionally removed, obtain an explicit AC/product decision with equivalent evidence rather than silently discarding it.
2. **RR-02 — qualified release-performance evidence (P0).** Restore/provision a Windows 11 reference-low-end self-hosted runner satisfying verifyPerformanceEnvironment.ts; pin final RC code, hardware, backend, dataset and workload; execute P0, P1, P2 collectors and their raw/metadata/evaluator sequence; retain artifacts and report each threshold unmodified. Run the required serial reference repeatability rounds per BASELINE-02, default and optional OpenGL separately. Diagnose genuine misses as new performance tasks instead of reducing samples or thresholds.
3. **RR-03 — platform acceptance (P0).** On macOS Intel/ARM, check native titlebar controls, IME candidate window at normal/narrow widths and table/contenteditable, context menus/shortcuts, save/reopen; record OS, CPU, input method, installer hash, screenshot or video, and pass/fail. Validate Windows native flows on exact RC. State explicitly that Linux is not in this release matrix.
4. **RR-05 — AC ledger signoff (P1 before Go).** Establish one canonical US/AC source and executable test pointers for all v0.5.0 acceptance conditions (including non-consecutive supplemental ACs). Mark each Passed, Deferred-by-approved-scope, Failed or Missing evidence. No inferred success from a feature title or old worktree.
5. **RR-04/RR-06 — prepare release candidate (P0).** Once product gates permit: version manifests to 0.5.0, lockfile/version/release notes consistency; run exact RC PR CI and three-platform packaging; assemble updater YAML, checksums and artifacts; install/run the produced packages; verify v0.4.1 → v0.5.0 update, unsaved-content safety, existing local history/recovery, failure/retry and no corruption. Confirm signing policy/user instructions. A published release is irreversible operational work; keep tag creation after explicit Go.
6. **RR-07 — visual acceptance (P1).** Replace stale reference screenshots only after reviewing current real UI in Light/Dark/Paper, narrow responsive layouts, editor/table/menus, settings, search and recovery; record approved differences. Do not bless product regressions as visual-baseline changes.
7. **RR-08 — maintenance (P2).** Review each dirty/stale worktree before removal; keep all non-integrated work. Run bounded full object-integrity/GC diagnosis without aggressive prune, keeping backups and repository refs safe.

### Required Go condition

Go only when RR-01 through RR-04 and applicable acceptance of RR-05/RR-06 are backed by **current exact-candidate evidence**, with no unresolved P0 product failures; supported macOS/Windows signoff, formal reference performance evaluation, release-install/upgrade safety, artifact integrity and a reviewed change log must all be independently recorded. Optional P3, cosmetic follow-ups and unrelated maintenance may be explicitly deferred without calling them passed.

Until then: **NO-GO, no v0.5.0 tag, no release.**

## 6. Audit-stage validation and limitations

This is an evidence audit, **not** a new full Electron, performance, macOS, installer or release execution. Read-only inspection covered Git refs/worktrees, story and architecture records, tag/version/release config, merged PR CI statuses, performance workflow runs and failure logs, runner inventory, updater verification and package smoke scripts. No platform-specific pass, fresh RC performance sample or test coverage not observed here is claimed.

Reusable lesson: **Feature PR green is not version release-green.** Keep per-story integration, target-OS native behavior, reference-hardware performance, artifact assembly and real upgrade safety as separate signed gates. Check branch-only user-story work before declaring a release scope complete.
