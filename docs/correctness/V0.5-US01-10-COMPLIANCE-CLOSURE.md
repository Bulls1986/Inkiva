## Stage 9 — shard 1 diagnostic closure: stale blocks readiness probe

Status: **root cause proven; test-observability fix applied; isolated full shard 1/4 Green**

Independent Red evidence:

- Governance full Electron shard 1/4 completed `101/102`; the only failure was `editor-switch-performance.spec.ts` — `switching back to an edited tab reuses its blocks snapshot`. The document content was preserved, but the activation metric reported `setContentSources=['markdown']` instead of the expected `['blocks']`.
- Final validation was then moved to the clean frozen worktree `v0.5-us01-10-validation` at snapshot `a95590a`. That physically separate worktree independently reproduced the exact same `101/102` result and the exact same sole assertion failure. This rules out governance `out/` overwrite, stale dirty source, and shared-worktree build interference as the cause.
- The validation worktree reuses a known-good dependency payload, so Playwright worker command lines can contain the governance `node_modules` path. That dependency-path reuse is not evidence that source or build output directories are shared; the validation worktree path is separate.

Root cause:

- The newly added readiness helper `currentTabHasReusableBlocks()` only checked whether Pinia `currentFile.blocks` was a non-empty array.
- After a text edit, the document revision advances immediately while the full derived snapshot is intentionally deferred by the `80ms/500ms` scheduler. During that window, `tab.blocks` may still contain the previous revision's non-empty block tree.
- The helper therefore could return true for stale pre-edit blocks. If the test switched tabs at that instant, `flushSnapshot(id, 'switch')` correctly captured Markdown/history only and cleared the stale reusable blocks cache. Returning to the tab then correctly used the Markdown fallback, making the test fail even though the product followed its intended snapshot contract.
- This is a test-observability race, not a `setContent`/tab-switch product regression. Changing product cache or switch semantics to force `blocks` would be the wrong-layer fix.

Minimal correction:

- No production code was changed for this failure.
- The E2E helper now waits until the persisted block snapshot itself contains the just-entered `edited` text, proving the observed snapshot belongs to the edited state instead of accepting any older non-empty block array.
- The original performance contract remains unchanged: once the current edited warm snapshot exists, returning to the tab must use `blocks`, perform exactly one `setContent`, and avoid Markdown serialization.

Focused Green evidence:

- Created tracked frozen snapshot `c1f881b` from the governance worktree without modifying the governance branch or working tree. Exact tree comparison against failed snapshot `a95590a` shows only this E2E test and this stage record changed; product source is identical.
- On `c1f881b`, the previously failing case passed `1/1` in `9.9s` with the original `setContentSources=['blocks']`, single-`setContent`, and zero-Markdown-serialization assertions unchanged.
- Because product source is byte-identical to the already-built `a95590a` snapshot, this focused test reused the existing Electron build; no rebuild was needed to validate a test-only readiness correction.

Next authoritative evidence:

- Full isolated shard 1/4 on `c1f881b` passed `102/102` in `6.3m`; the edited-tab blocks-snapshot case passed inside the complete shard with the original assertions intact.
- Do not use fixed sleeps, relax the `['blocks']` assertion, or modify product switch/cache semantics to make the test pass.
